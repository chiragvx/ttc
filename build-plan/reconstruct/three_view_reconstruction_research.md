# 3-view → solid reconstruction (extrude+intersect, revolve-branch) — prior-art research

**Date:** 2026-08-03
**Status:** Exploratory research only — nothing here is built or scheduled. Captured so future work
doesn't re-derive it from scratch.

## Context / the idea being evaluated

A "body maker" that takes a 3-view PNG (front/top/side, e.g. an internet-sourced product photo set),
auto-identifies the 3 views, extrudes each view's silhouette along its own viewing axis, boolean-
intersects the three extrusions to get a merged solid, then applies fillet/chamfer to clean up the
result. A follow-up refinement: some shapes (e.g. a wine bottle) are actually solids of revolution —
detectable because their front-view and side-view silhouettes match and the top view is circular —
in which case the pipeline should branch to a `revolve()` instead of a generic 3-way intersect, since
a matched profile is an *exact* reconstruction for a true body of revolution (no visual-hull ambiguity).

Four parallel research agents (Sonnet 5, via the Workflow tool) investigated: (A) build123d/CadQuery-
specific precedent, (B) the technique in any CAD tool, (C) the correct academic/algorithmic name and
its known limitations, (D) revolve/axisymmetry-detection precedent specifically. A fifth agent
synthesized the four raw reports. Everything below is copied verbatim from that research (own analysis
by the orchestrating session is in the final "Bottom line" section only) — citation status (directly
fetched vs. search-snippet-only vs. recalled/unverified) is preserved exactly as each agent reported it.
No URL below was invented; each was actually retrieved via WebSearch/WebFetch in that session.

### 2. The technique's real name(s), and whether it's established elsewhere

Two distinct names attach to two distinct literatures (per Agent C), and both are independently
corroborated by Agent B's tool-level findings:

- **CV/graphics name**: "shape from silhouette" / **"visual hull"** (Laurentini, 1994) and
  **"space carving"** (Kutulakos & Seitz, 1998) — multi-view silhouette-intersection, usually with many
  views of a real photographed object, not specifically 3.
- **CAD/engineering name**: "3D reconstruction from (2D) orthographic views" / "solid model
  reconstruction from three-view engineering drawings" — a distinct subfield dating to the 1970s–80s
  that works from full line drawings (including hidden/dashed lines), which is strictly more
  information than a pure silhouette.

**It has a named, published, exact match**: Agent B found **Rivers, Durand, Igarashi,
"3D Modeling with Silhouettes,"** ACM SIGGRAPH 2010 — retrieved and read the
[PDF](https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_silhouette.pdf) directly, plus
corroborating [ACM DL record](https://dl.acm.org/doi/10.1145/1778765.1778846),
[ResearchGate](https://www.researchgate.net/publication/220184390_3D_Modeling_with_Silhouettes), and a
[demo video](https://www.youtube.com/watch?v=9cLEg2SXDdM). Confirmed by the fetched text: each 2D
silhouette from front/side/top is extruded ("swept into a generalized cylinder") along its viewing
axis, and the final shape is the CSG intersection of all three, computed via a specialized fast 2D
algorithm rather than general 3D booleans. Agent B calls this "essentially exact" to the user's
question. It is a research prototype, not a shipped product.

**It's a real, working, named add-on**: [Shadowbox](https://github.com/D4KU/shadowbox) (Blender),
confirmed via README fetch — generates a mesh from 3 per-axis silhouette images using a custom
C++/OpenVDB volumetric backend. Agent B could not confirm the internal op is literally "extrude then
boolean intersect" vs. an equivalent SDF/volume combination, but functionally it's the same technique,
live and installable today.

**It's a native, first-class operation in mainstream commercial CAD**: SolidWorks' **Intersect tool**
([engineersrule.com](https://www.engineersrule.com/overlooked-but-useful-solidworks-tools-intersect/),
[store.trimech.com](https://store.trimech.com/blog/solidworks-intersect-tool)) is documented for
exactly this "solids from intersecting regions of extrusions on different planes" use, and Fusion 360's
Extrude feature natively supports Join/Cut/Intersect across separate sketches (Autodesk community
threads/help pages). Neither is branded as "3-view blueprint reconstruction," but the underlying
operation is first-class, no plugin required.

**Not found**: no dedicated FreeCAD workbench doing this (TechDraw goes the opposite direction, 3D→2D);
no Blender core feature; no mass-market commercial "photo/blueprint→3D" product using this geometric
mechanism (the "photo-to-3D" products Agent B found — Meshy AI, 3D AI Studio, Planner5D — are
generative-AI or floorplan tools, unrelated mechanism).

### 3. Academic/algorithmic grounding and known limitations (the concavity question)

Agent C's research directly answers this and largely **confirms** the stated limitation, with an
important precision:

- **For pure-silhouette reconstruction, "invisible concavity gets silently lost" is a proven theorem,
  not just an observed engineering gap.** Laurentini's 1994 visual-hull theory establishes that any
  concave surface patch that never appears on the silhouette boundary from *any* viewpoint is provably
  unrecoverable by any silhouette-based method, no matter how many views are added — this is the
  theoretical ceiling of the entire shape-from-silhouette family. (Sourced from search-snippet
  paraphrase — Agent C could not get WebFetch to return actual abstract text from Semantic
  Scholar/ADS, so exact wording isn't independently verified, but the claim itself is treated as
  settled/uncontested in the field.) A space-carving summary corroborates independently: "The
  Shape-From-Silhouette method cannot remove the voxels in the concave regions that do not appear in
  the silhouette images."
- One paper looks like a direct hit on the exact three-view scenario: **"A 3D modeling methodology
  based on a concavity-aware geometric test to create 3D textured coarse models from concept art and
  orthographic projections"** (VeRLab/UFMG, *Computers & Graphics* 2018) —
  [project page](https://www.verlab.dcc.ufmg.br/from-2d-to-3d-by-drawing/) (fetched, thin content) and
  [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0097849318301365) (403, could
  not fetch full text; relying on search snippet). This paper's whole premise, per the snippet, is that
  carving-based methods "are not able to model concave regions," and it was built specifically to fix
  that gap for the three-view (front/side/top) concept-art case. Closest single match found, but
  blocked from reading full text (ScienceDirect paywall).

**Important qualifier**: this concavity-loss result applies most precisely to *pure silhouette/outline*
input. For actual **engineering line drawings** (with hidden/dashed lines encoding internal edges), the
literature's more heavily documented failure mode is different — **non-uniqueness / "ghost solid"
ambiguity**: multiple distinct valid solids can project to the same three views. Documented across four
decades: Wesley & Markowsky, "Fleshing Out Projections," IBM J. Res. Dev. 1981 (snippet-sourced, direct
PDF fetch failed); Sakurai & Gossard, "Solid Model Input through Orthographic Views," SIGGRAPH 1983
(directly fetched from [history.siggraph.org](https://history.siggraph.org/learning/solid-model-input-through-orthographic-views-by-sakurai-and-gossard/):
"When the projections are ambiguous, multiple solid models are produced"); an IntechOpen chapter
(directly fetched, [intechopen.com/chapters/72385](https://www.intechopen.com/chapters/72385)): "up to
now, there is still not any software that can do it as thoroughly as we have been expecting," and flags
that "elimination of all the invalid candidate objects is often incomplete"; and arXiv 2412.11892 (Dec
2024, directly fetched, [arxiv.org/html/2412.11892v1](https://arxiv.org/html/2412.11892v1)), confirming
industry still does this largely by manual labor as of late 2024 and that even recent automated methods
impose restrictive assumptions (exactly 3 clean axis-aligned views, annotations stripped).

**Bottom line on this sub-question**: if the pipeline works from pure outlines/silhouettes, the
concavity-loss claim is the textbook, proven visual-hull limitation. If hidden-line data is ever added,
concavities become partially recoverable, but the overall three-view→solid map still isn't guaranteed
unique — disambiguation remains an actively-published, open problem as of 2024.

### 4. Revolve/axisymmetry-detection precedent (the wine-bottle case)

Clearest split into "old, adjacent, partially-verified" vs. "new, directly relevant, but assumes rather
than detects":

**Old CAD literature (1980s–2000s) that branches extrude vs. revolve, but not via the exact
front/side/top-circularity heuristic** — every full-text host (ScienceDirect, ResearchGate, Springer)
403'd for Agent D, so all of the following are title/abstract/search-snippet level only:
- Chen & Perng, "Automatic reconstruction of 3D solid objects from 2D orthographic views," *Pattern
  Recognition* 21(5):439-449, 1988 — per snippet, reconstructs polyhedra, cylinders, partial cylinders,
  composites via decomposition → reconstruction (translation-sweep, plane-cut) → composition;
  functionally an extrude-vs-revolve branch but driven by primitive-type decomposition, not
  silhouette-congruence testing.
- "Handling Solids of Revolution in Volume-Based Construction of Solid Models From Orthographic Views"
  — per snippet, proposes recognizing solids of revolution but explicitly **restricted to cases where
  the revolution axis is normal to one of the three projection planes** (i.e., exactly the "top view is
  circular" precondition) — closest title match found, but unverified beyond the snippet.
- "Reconstruction of 3D models from 2D orthographic views using solid extrusion and revolution" — per
  snippet, closest literal match to "branch to revolve instead of generic extrude-intersect": features
  built by both extrusion and revolution, decided per-feature from the three views, then combined by
  boolean ops. Unverified beyond search synthesis.
- Related titles found but not fetched: "Reconstruction of 3D interacting solids of revolution from 2D
  orthographic views," "Solid reconstruction using recognition of quadric surfaces from orthographic
  views."
- A field-level synthesis confirms axis-alignment-to-a-projection-plane (⇒ circular view) is the
  standard enabling assumption this whole subfield relies on.

**New, directly relevant, but solving a different half of the problem**: **SOR3D — "Single-view 3D
reconstruction of surface of revolution,"** *The Visual Computer*, 2025 — confirmed by direct fetch of
the [project page](https://smh-hosseiny.github.io/SOR-3D/) and the
[GitHub repo](https://github.com/smh-hosseiny/SOR_3D_Reconstruction) (code public). Reconstructs
axisymmetric objects (vases, bottles, containers) from a single photo by solving for the 3D symmetry
axis that matches the input silhouette, plus texture transfer. Critically: **it assumes axisymmetry is
given** (test objects are curated single-object-of-revolution images from Pix3D/BigBIRD); it does not
decide whether an arbitrary input object is bottle-like before applying the method. A likely
predecessor, "Reconstruction of Surfaces of Revolution from Single Uncalibrated Views" (ScienceDirect,
all hosts blocked), follows the same pattern per snippet.

**Explicitly not found**: no paper or tool stating the precise heuristic — "front/side silhouettes
match AND top view is circular ⇒ branch to revolve" — as an automatic decision rule. Nothing combining
automatic axisymmetry *detection* with a 3-view extrude-intersect pipeline. Nothing on CadQuery/
build123d plus any image-derived revolve-profile workflow. No commercial bottle-photo-to-3D tool
assuming/detecting axisymmetry this way.

### 5. Bottom-line verdict

- **"Extrude each of 3 orthographic-view silhouettes and boolean-intersect them"** — established and
  named: peer-reviewed SIGGRAPH 2010 "3D Modeling with Silhouettes," a real shipping Blender add-on
  (Shadowbox), native first-class tooling in SolidWorks and Fusion 360, decades of CAD-literature
  lineage, and a rigorous theoretical ceiling (Laurentini's visual hull).
- **"...on build123d or CadQuery specifically"** — **not found anywhere**, across three independent
  search passes. Strongest, most consistent finding across all four reports. Caveat: GitHub code
  search and grep.app were both effectively inaccessible this session.
- **"...concavities invisible in all views get silently fabricated"** — **confirmed as a proven
  limitation** for the pure-silhouette case, with the caveat that hidden-line/dashed-edge input shifts
  the dominant failure mode to non-uniqueness/"ghost solid" ambiguity instead.
- **"...branch to revolve when the top view is circular"** — **a genuine gap, not solved prior art**.
  Old CAD literature branches extrude vs. revolve per-feature under an axis-normal-to-a-projection-plane
  assumption (unverified beyond snippets); SOR3D (confirmed live) handles single-photo axisymmetric
  reconstruction assuming axisymmetry — but no report found any work combining automatic axisymmetry
  *detection from 3-view silhouette congruence* with a branching decision into a revolve op inside an
  extrude/intersect pipeline.

**So**: the individual pieces of this pipeline are each well-established in some corner of CAD research
or mainstream tooling — but no report found the specific combination assembled, and no report found any
of it built on build123d or CadQuery. This is a **known-technique, unimplemented-in-build123d
combination**, not something novel in concept: the "extrude+intersect from 3 views" core is thoroughly
prior-arted elsewhere (just not on this stack), the concavity limitation is textbook-proven (for the
silhouette case), and the revolve-branch-via-axisymmetry-detection piece specifically looks like a
genuine, unclaimed gap. Given the search gaps every agent flagged (GitHub code search unauthenticated,
grep.app rate-limited, most CAD-reconstruction full texts paywalled, Discord unindexed), read this as
"nothing surfaced despite a real effort to find it," not an airtight proof of absence.

### Agent B — the technique in ANY CAD tool, not just build123d

## Research Findings: 3-View Silhouette-Extrusion-Intersection as a CAD Technique

**Verdict up front: yes, solid prior art exists** — as an academic research prototype, as at least one
real working open-source add-on, and as a documented (if not identically-named) workflow inside
mainstream commercial CAD tools. It is not something found marketed end-to-end as a mainstream
"photo/blueprint → 3D" commercial product, but the core technique is well established in several
concrete, real, retrievable places.

### 1. Academic origin — "3D Modeling with Silhouettes" (Rivers, Durand, Igarashi — MIT CSAIL, ACM SIGGRAPH 2010)
This is the closest and most authoritative match to exactly what's being asked about.
- Retrieved and read: https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_silhouette.pdf
- Also found (not separately fetched, but corroborating): ACM DL record
  https://dl.acm.org/doi/10.1145/1778765.1778846 , ResearchGate
  https://www.researchgate.net/publication/220184390_3D_Modeling_with_Silhouettes , demo video
  https://www.youtube.com/watch?v=9cLEg2SXDdM
- What it actually does: the user sketches a part's silhouette in the front, side, and/or top view;
  each silhouette is swept into a "generalized cylinder" (i.e., extruded) along the corresponding
  viewing axis; the 3D shape is the **CSG intersection** of these extruded volumes, computed via a
  specialized fast 2D algorithm rather than general 3D boolean ops. Confirmed by the fetched PDF: "Each
  2D silhouette from a single orthographic view is extruded into 3D space perpendicular to its viewing
  plane... The extruded volumes from all three orthographic views are intersected together, producing
  the final 3D model." This is a research prototype (interactive sketch-modeling system), not a shipped
  commercial product.
- Closeness to the question: essentially exact — this is the named/published version of precisely the
  technique described.

### 2. Real, working, named tool — "Shadowbox" (Blender add-on, D4KU)
- Retrieved: https://github.com/D4KU/shadowbox
- What it does (from the README): "a Blender add-on to generate a mesh from 3 images describing its
  silhouette from each axis." User assigns one image per axis (front/side/top-equivalent), and the
  add-on generates the 3D mesh from those three silhouettes, using a custom C++/OpenVDB-based backend

### Agent C — the academic/algorithmic name and prior art for the technique itself

## Findings

**Search performed via WebSearch/WebFetch this session; URLs below were actually returned/retrieved,
not reconstructed from memory.**

### 1. What the technique is actually called

There are **two distinct literatures**, and it matters which one the technique falls into:

- **Computer vision**: "shape from silhouette" / "visual hull" (Laurentini, 1994) and "space carving"
  (Kutulakos & Seitz, 1998) — multi-view (usually many, not just 3) silhouette-based volume
  intersection, typically for photographs of real objects from many angles around them.
- **CAD/engineering**: "3D reconstruction from (2D) orthographic views," "engineering-drawing
  interpretation," or "solid model reconstruction from three-view engineering drawings" — a distinct
  subfield going back to the 1970s–80s, working from *line drawings* (which include hidden/dashed
  lines, not just outlines).

These are not the same problem even though both start from ~3 orthographic images: engineering
drawings encode internal/hidden edges as dashed lines, which is strictly more information than a pure
silhouette.

Key retrieved sources:
- ResearchGate/ScienceDirect/IntechOpen listings for "3D Solid Reconstruction from 2D Orthographic
  Views" (https://www.intechopen.com/chapters/72385, fetched directly) — confirms the CAD-side term and
  traces the field to the 1970s.
- Laurentini, "The Visual Hull Concept for Silhouette-Based Image Understanding," IEEE TPAMI 1994
  (https://www.researchgate.net/publication/3192242_The_Visual_Hull_Concept_for_Silhouding-Based_Image_Understanding,
  https://dl.acm.org/doi/10.1109/34.273735,
  https://ui.adsabs.harvard.edu/abs/1994ITPAM..16..150L/abstract) — this is the paper that coined
  "visual hull" and gave it a formal theory. (WebFetch could not return the actual abstract text —
  Semantic Scholar and ADS both returned empty bodies — so relying on the search-snippet paraphrase, not
  a verified verbatim quote, for exact wording.)
- Kutulakos & Seitz, "A Theory of Shape by Space Carving," IJCV 1998/2000 (PDF fetched via search:
  https://www.ri.cmu.edu/pub_files/pub1/kutulakos_k_n_1998_2/kutulakos_k_n_1998_2.pdf,
  https://link.springer.com/article/10.1023/A:1008191222954) — the space-carving paper proper.

### 2. Is it solved or open?

**Not solved**, on both sides of the literature, and this is stated explicitly, not inferred:

- IntechOpen chapter on 3D solid reconstruction from orthographic views (fetched directly,
  https://www.intechopen.com/chapters/72385): *"up to now, there is still not any software that can do
  it as thoroughly as we have been expecting,"* despite work since the 1970s. Also flags that
  "elimination of all the invalid candidate objects is often incomplete" — i.e., spurious ("ghost")
  solids remain a live problem.
- arXiv 2412.11892, "From 2D CAD Drawings to 3D Parametric Models" (Dec 2024, fetched directly,
  https://arxiv.org/html/2412.11892v1): confirms that as of late 2024, industry still does this largely
  by manual labor — "time-consuming, error-prone, and unproductive" — and that even recent automated
  methods impose restrictive assumptions (exactly 3 clean axis-aligned views, annotations stripped
  out). This is a live, current research area (vision-language-model-based approaches are the newest
  attempt), not a closed textbook problem.

### 3. Confirming/correcting the concavity claim

The framing — **concavities invisible in all three silhouettes get silently filled in / cannot be
reconstructed** — is **correct, and it is a proven theorem, not just an observed engineering gap**, but
it applies most precisely to the *pure-silhouette* (visual-hull / space-carving) formulation, not
necessarily to full engineering line-drawing reconstruction where hidden-line dashes exist:

- Laurentini's visual hull theory (per search-result paraphrase of the 1994 paper): the visual hull is
  *"the maximal object silhouette-equivalent to S, which can be substituted for S without affecting any
  silhouette"* — i.e., **any concave surface patch that never appears on the silhouette boundary from
  any viewpoint is provably unrecoverable by any silhouette-based method, no matter how many views you
  add.** This is the theoretical ceiling of the whole shape-from-silhouette family.
- Space-carving search summary, corroborating independently: *"The Shape-From-Silhouette method cannot
  remove the voxels in the concave regions that do not appear in the silhouette images."*
- A directly on-point paper: "A 3D modeling methodology based on a concavity-aware geometric test to
  create 3D textured coarse models from concept art and orthographic projections" (VeRLab/UFMG,
  Computers & Graphics 2018) — https://www.verlab.dcc.ufmg.br/from-2d-to-3d-by-drawing/ (fetched, thin
  content) and https://www.sciencedirect.com/science/article/abs/pii/S0097849318301365 (403, could not
  fetch full text; relying on search snippet). This paper's whole premise, per the snippet, is that
  carving-based methods "are not able to model concave regions," and it was built specifically to fix
  this gap for the three-view (front/side/top) concept-art case — essentially the exact scenario
  described. This is the closest single match found, but blocked from reading the full text
  (ScienceDirect paywall), so cannot confirm the internal mechanics beyond the abstract-level claim.

**Caveat for the engineering-drawing side**: in that literature the dominant *named* limitation is not
"concavity gets filled in" but **non-uniqueness/ambiguity — multiple distinct valid solids project to
the same three views ("ghost" objects)**:
- Wesley & Markowsky, "Fleshing Out Projections," IBM J. Res. Dev. 1981 (search-confirmed via
  https://dl.acm.org/doi/abs/10.1147/rd.256.0934,
  https://www.researchgate.net/publication/224104093_Fleshing_Out_Projections; direct PDF fetch failed
  with a connection error, so this is snippet-sourced) — the foundational paper; explicitly built to
  enumerate valid solids from wireframes, precisely because that mapping isn't unique.
- Sakurai & Gossard, "Solid Model Input through Orthographic Views," SIGGRAPH 1983 (fetched
  https://history.siggraph.org/learning/solid-model-input-through-orthographic-views-by-sakurai-and-gossard/):
  *"When the projections are ambiguous, multiple solid models are produced"* — the system deliberately
  outputs several candidate solids rather than one.
- Taylor & Francis reference entry on wire-frame models (search snippet,
  https://taylorandfrancis.com/knowledge/Engineering_and_technology/Computer_science/Wire-frame_models/):
  names two "major weaknesses" of wireframe-based reconstruction: non-validity (impossible/Escher-like
  objects) and **ambiguity** ("a valid model to be interpreted as representing more than one real-world
  object").

So: if the pipeline works from pure outline/silhouette images (no hidden-line/internal-edge data), the
concavity claim is exactly the textbook visual-hull limitation, proven, not disputable. If it works
from actual three-view engineering drawings with hidden lines, the literature's more precise and more
heavily documented failure mode is broader non-uniqueness/"ghost solid" ambiguity — concavities are
*often* recoverable there via dashed hidden-line edges, but the overall three-view-to-solid map still
isn't guaranteed unique, and disambiguating it (extra views, section views, heuristics, human input)
remains an open, actively-published problem as of 2024.

## Verdict

Solid prior art exists for this sub-question, on both flanks: Laurentini's 1994 visual-hull theorem is
a rigorous, decades-old, uncontested result that precisely matches the "concavity invisible in all
views is silently lost" claim for silhouette-based reconstruction; and the separate 1980s-to-present CAD
engineering-drawing-reconstruction literature (Wesley & Markowsky 1981, Sakurai & Gossard 1983, through
IntechOpen 2020 and arXiv Dec-2024) documents the closely related but distinct non-uniqueness/"ghost
solid" problem as still unsolved in general, automatic form. The one gap in verification: could not get
full-text access to the single paper (VeRLab/Computers & Graphics 2018) that most directly targets the
exact three-orthographic-view/concavity framing — that claim rests on a search-snippet paraphrase, not
a verified full read.

### Agent D — revolve/axisymmetry detection specifically

## Findings: 3-view orthographic reconstruction + automatic axisymmetric/revolve detection

### Bucket 1 — Multi-view (3-orthographic-view) engineering CAD reconstruction with a revolve/extrude branch

This is an established sub-line of the "reconstruct 3D solids from front/top/side engineering
drawings" literature (1980s–2000s), and it is close to what's being asked, though framed in CSG/graph-
matching terms rather than "silhouette congruence + circular top view."

- **Chen & Perng, "Automatic reconstruction of 3D solid objects from 2D orthographic views,"**
  *Pattern Recognition* 21(5):439-449, 1988. Found via WebSearch (ScienceDirect abstract page
  `sciencedirect.com/science/article/abs/pii/0031320388900039`, Harvard ADS
  `ui.adsabs.harvard.edu/abs/1988PatRe..21..439C/abstract`, Semantic Scholar, ACM DL) — full text was
  blocked (403) at every host tried, so this is from the search-result abstract snippet, not a direct
  fetch. Per that snippet: the algorithm reconstructs polyhedra, **cylinders, partial cylinders, and
  composites** automatically from views containing lines/circles/arcs, via a decomposition →
  reconstruction (translation-sweep, plane-cut) → composition pipeline. This is functionally a
  revolve-vs-extrude branch driven by which primitive a subview decomposes into, but it's not framed as
  "match front/side silhouettes + check top-view circle."

- **"Handling Solids of Revolution in Volume-Based Construction of Solid Models From Orthographic
  Views"** — title found via WebSearch (ResearchGate), full text blocked (403). Per the search engine's
  synthesized snippet: proposes a **hint-based method to recognize interacting (not just isolated)
  solids of revolution**, but explicitly **restricted to axis-aligned cases where the revolution axis
  is normal to one of the three projection planes** — i.e., exactly the "top view is circular"
  precondition in the question. Could not verify this beyond the snippet.

- **"Reconstruction of 3D interacting solids of revolution from 2D orthographic views"** —
  ScienceDirect (`sciencedirect.com/science/article/abs/pii/S0010448505000205`), likely a
  follow-up/companion to the above by title; full text 403-blocked, not independently verified beyond
  the title/search listing.

- **"Reconstruction of 3D models from 2D orthographic views using solid extrusion and revolution"** —
  ScienceDirect/ResearchGate, full text 403-blocked. Per the WebSearch synthesis: features are built by
  **both extrusion and revolution operations**, decided per-feature after evaluating geometric entities
  (via a DXF translator) on the three views, then solids are combined by boolean
  intersection/subtraction. This is the closest literal match to "branching to revolve instead of
  generic extrude-intersect" found — but again only the search engine's summary, not verified full
  text.

- **"Solid reconstruction using recognition of quadric surfaces from orthographic views"** —
  ScienceDirect, title-only; quadric surfaces (cylinder/cone/sphere) are exactly the revolve family, but
  not fetched.

- A synthesized line from the first search batch (attributed to this literature as a whole, not one
  paper) is worth flagging as a real finding-about-the-field even though it's a paraphrase: CSG-oriented
  reconstruction approaches "are generally applicable only to mechanical parts of uniform thickness or
  **axis-aligned volumes of revolution**" — confirming that axis-alignment-to-a-projection-plane (⇒
  circular view) is the standard enabling assumption this whole subfield relies on, not something more
  general like the silhouette-congruence test.

**Caveat:** every full-text host (ScienceDirect, ResearchGate, Springer) 403'd on WebFetch in this
session. Everything in this bucket beyond the bare existence/title of the papers comes from WebSearch's

### Bucket 2 — Single-view reconstruction assuming axisymmetry (the actual "wine bottle from one photo" case)

- **SOR3D — "Single-view 3D reconstruction of surface of revolution,"** *The Visual Computer*, 2025.
  **Confirmed by direct WebFetch** of the project page (`smh-hosseiny.github.io/SOR-3D/`) and GitHub
  repo (`github.com/smh-hosseiny/SOR_3D_Reconstruction`, code public). This is a real, direct hit:
  reconstructs axially symmetric objects — **vases, bottles, containers** shown on the project page —
  from a **single photograph**, by solving an optimization for the 3D axis of rotational symmetry that
  makes the reconstructed body's projection match the input silhouette, plus a texture-transfer step.
  Critically: **it assumes axisymmetry is given** (test objects are curated SOR images from
  Pix3D/BigBIRD) rather than automatically detecting whether an arbitrary object is axisymmetric before
  deciding to use this method — so it solves "reconstruct given it's a bottle" but not "decide it's a
  bottle-like part vs. some other shape."

- **Predecessor: "Reconstruction of Surfaces of Revolution from Single Uncalibrated Views"** (older,
  ScienceDirect `S0262885604000502`, HKU repository PDF) — all hosts blocked/empty on fetch. Per
  WebSearch synthesis: uses invariant properties of a silhouette to locate the revolution axis and
  calibrate focal length, then rectifies the image to bilateral symmetry for depth recovery. Same
  pattern as SOR3D: assumes SoR as a given prior, doesn't auto-detect it.

- **"Exploiting Symmetry and/or Manhattan Properties for 3D Object Structure Estimation from Single and
  Multiple Images"** (arXiv 1607.07129) — found by title only, not fetched; likely relevant to
  symmetry-prior estimation generally but not CAD/revolve-specific, and not verified beyond the title.

### What was explicitly NOT found

- No paper or tool stating the precise heuristic — "front-view and side-view silhouettes match AND top
  view is circular ⇒ branch to revolve instead of generic extrude+intersect" — as an explicit automatic
  decision rule in a reconstruction pipeline. The nearest things are (a) the 1980s–2000s CSG/
  orthographic-view literature above, which does branch per-feature between extrude and revolve but
  reasons over line/circle graph-matching rather than a silhouette-congruence test, and (b) standard
  engineering-drawing pedagogy (top view = circle, front/side = identical rectangles ⇒ cylinder) which
  is textbook drafting knowledge, not a specific automatic-detection research citation.
- Nothing on CadQuery or build123d combined with any image-derived revolve-profile workflow — searched
  directly, found only generic revolve API docs/forum posts, no image→profile→revolve pipeline.
- No confirmed commercial product-photography tool that explicitly assumes axisymmetry to go from one
  bottle photo to a 3D model — the SOR3D research prototype above is the real analogue that could be
  substantiated; searches for a commercial equivalent returned only unrelated turntable-MVS and medical-
  vessel-imaging results.
- A WebSearch synthesis (not a verified quote) around Text2CAD-Bench (arXiv 2605.18430) suggested
  current LLM text-to-CAD systems lack advanced-feature handling generally — flagging this as
  recalled-from-search-synthesis, not independently verified via full-text fetch.

### Verdict

Partial prior art exists, split across two disconnected bodies of work: (1) 1980s–2000s orthographic-
view CAD reconstruction papers that do branch between extrude and revolve per-feature (but via
line/circle graph matching, axis-aligned-to-projection-plane assumption, and existence/titles only
verified, not full method detail, due to paywalls); and (2) a 2025 single-image axisymmetric
reconstruction system (SOR3D, confirmed live) that handles bottles/vases but assumes axisymmetry rather
than detecting it. **No work found that combines the two** — i.e., no confirmed automatic "detect
axisymmetry from 3-view silhouette congruence + circular top view, then branch a 3-view reconstruction
pipeline into a revolve op" — so the specific combination investigated appears to be a genuine gap
rather than solved prior art, built out of adjacent-but-separate pieces.
